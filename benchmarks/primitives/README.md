# primitives - gas micro-benchmarks of Cairo building blocks

Empirical Sierra-gas cost of the primitives a fixed-point linear algebra library is made of:
integer arithmetic per type, conversions, bitwise operators, control flow, data structures,
classic integer algorithms and inlining. Toolchain: scarb 2.19.4 / corelib 2.19.4, snforge 0.61.0.

The question to settle (project owner's hypothesis): **in Cairo, simple math (add, mul, divmod) is
cheaper than bitwise ops (and/or/xor), which are cheaper than loops.** Short answer: *mostly true,
with four precise exceptions* - see [Findings](#findings--rules-of-thumb).

```sh
cd benchmarks
snforge test -p primitives 2>&1 | python3 scripts/gas_report.py --md primitives/GAS.md
# explain a number (steps / builtins actually executed):
snforge test -p primitives <filter> --tracked-resource cairo-steps --detailed-resources
```

`GAS.md` holds the full report (107 groups, 763 measurements). Everything below is curated from it.

## Layout

| `src/control.cairo` | `loop_sum<N>`, `loop_fixed<N>`, `branch_u64` | loop flavours vs unrolled, branches |

Repetitive files are generated by `tools/gen_*.py` (expected values are computed in Python, so each
benchmark is also a correctness test). Regenerate with
`for g in tools/gen_*.py; do python3 $g; done && scarb fmt -p primitives` (output is byte-for-byte
reproducible). Non-benchmark `test_*` functions cross-check the hand-written algorithm variants
against each other and against corelib.

## Methodology

- One snforge test per measurement, named `bench_<group>__<variant>`; `net = raw - baseline` where
  the group baseline has the same black-boxed inputs and the same kind of assertion, minus the
  operation. Sierra gas is deterministic: one run is enough.
- Inputs go through `harness::black_box` (`#[inline(never)]` identity); results are asserted.
  Functions under test are plain `pub fn` (the compiler inlines them; checked in the Sierra).
- **Every benchmark test is `#[inline(never)]`.** snforge wraps each test in a generated
  `..__snforge_internal_test_generated` function and the compiler inlines *some* test bodies into
  it and not others. That silently adds or removes ~1,020 gas (one function call) on one side of a
  `raw - baseline` subtraction (we first measured `u64 mul_const` = 1,490 vs `mul` = 470 for
  identical Sierra). Forcing the attribute makes all tests pay the same call.
- `l2_gas` is Sierra gas as metered by the compiled program (what Starknet charges). Observed
  weights: 1 Cairo step = 100, 1 range check = 70, 1 bitwise builtin = 583. It is slightly *above*
  `100 x steps + builtins` actually executed because gas is pre-charged per branch.
- **First-use vs marginal cost.** A single operation measured against an operation-free baseline
  also pays one-off costs: a new implicit (`RangeCheck`, `Bitwise`) threaded through the function,
  a new panic path, branch alignment. The `marginal_<T>` groups chain the same operation 1x and 9x
  (`r = r op b`, each step depending on the previous one) and report both. Tables below show
  `first / marginal` where `marginal = (net(x9) - net(x1)) / 8`. Real numeric code looks like the
  marginal case; isolated helpers look like the first-use case.
- Costs are for the executed path (successful, non-panicking). Signed operations branch on signs, so
  they are measured for negative and positive operands (`*_pos`).
- Resolution: ±100-200 gas of layout noise (which branch falls through, store_temp placement). Do
  not read anything into differences below ~200 gas. A net of 0 or slightly negative (conversions)
  means "free": the variant's assertion compares a cheaper type than the baseline's.

`Checked/Wrapping/Overflowing/Saturating{Add,Sub}` but **no `*Mul` variants**, **no bitwise
operators**, no `Sqrt`. felt252 has no `/`, `%` (only `felt252_div`, a field division) and no
ordering. There is **no `Shl`/`Shr`** trait nor shift libfunc for any type.

### 3. `BoundedInt` (`core::internal::bounded_int`, feature `bounded-int-utils`)

| kernel | native best | BoundedInt | gain |
|---|---:|---:|---:|
| Q32.32 unsigned mul on u64 (`wide_mul`, `/ 2^32`, narrow) | 1,850 | **1,380** | -25% |
| same, naive through `u128 *` / through u256 | 4,880 / 20,750 | | |
| Q32.32 signed mul on i64 (`wide_mul`, `i128 / 2^32`, narrow) | 2,990 (2,790 pos.) | **1,850** (floor, branchless) / 2,350 (trunc) | -38% |
| sign-magnitude struct `{ mag: u64, sign: bool }` mul | 2,760 | 2,290 | -17% |
| Q64.64 unsigned mul on u128 (limbs of `u128_wide_mul`) | 10,480 (naive u256 `/`: 11,280) | **4,510** | -57% |
| dot product of 3-vectors, u64 Q32.32 (wide accumulate, one rescale) | 2,790 (naive 3 x fpmul: 9,290) | **1,780** | -36% |
| dot product of 3-vectors, i64 Q32.32 | 6,260 (naive: 12,580) | **2,250** | -64% |
| `a + b + c + d` on u64, single final check | 1,310 (via felt252: 740) | **570** | -56% |
| checked `x << 64` on u128 | 3,130 (`u128 *`) | **370** | -88% |
| `x >> 64` / low 64 bits of u128 | 1,380 (`/`, `%`) | **910** | -34% |
| `x >> k` / low bits on u64 | 910 | 910 | none (corelib already uses it) |

How it works: `bounded_int::mul/add/sub` track exact ranges in the type and cost one felt
operation (~100 gas, **no range check, no panic path**); `div_rem` by a constant costs ~900;
only the final `downcast` to the storage type is checked. The signed "floor" kernel biases the
product by `2^126` so that a single unsigned `div_rem` implements an arithmetic shift right without
branching on the sign (note: floor semantics, `-1 ulp * 0.5 = -1 ulp`, whereas `i128 /` truncates
to 0 - both are covered by `test_fpmul_i64_semantics`). `div_rem` accepted a dividend above
`2^128` (3 accumulated i64 products).

## Findings & rules of thumb

**Verdict on the hypothesis (math < bitwise < loops).**

1. *add / sub / mul < bitwise*: **true up to 64 bits.** u64 `+`/`*` cost 370 first-use and 745 at
   the margin; `&`/`|`/`^` cost 1,583 first-use and 895 at the margin (a bitwise builtin call is
   583 gas by itself, vs 70 for a range check). Math wins by x4.3 isolated and x1.2 in long chains.
2. *divmod < bitwise*: **a tie, context decides.** u64 `/`, `%`, `DivRem` = 910 first / 1,152
   marginal vs 1,583 / 895 for `&`. An isolated mask is cheaper as `% 2^k` (910 vs 1,683: the
   function must otherwise thread the `Bitwise` implicit); inside an already-bitwise function a
   mask is ~20% cheaper than a division. `DivRem` gives quotient and remainder for the price of one
   (610 vs 2,193 for `/` + `&`), which is what fixed-point code needs.
3. *math < bitwise* **fails for wide types**: a u128 `*` (3,030) costs 2-3.8x a u128 `&`; on u256,
   `%` (5,850) costs 2.3x `&` (2,566) and `*` costs 13,880. (Both lose to limb tricks: low bits of
   a u256 through its low limb = 610.)
4. *math < bitwise* **fails for data-parallel bit tricks**: SWAR popcount (14,612) beats the best
   math version (43,240) x3. When one bitwise op replaces many divisions, it wins.
5. *bitwise < loops*: **true, by a wide margin.** One loop iteration costs ~1,100 gas of overhead
   (plus ~1,200 per loop) before doing any work, i.e. more than any 64-bit primitive. Every loop
   version lost: msb x21, popcount x8.5, sqrt x125, pow2 x58, is_pow2 x33 vs the best alternative.
6. Above all three: **hint-backed libfuncs and tables.** corelib `Sqrt` (1,080) is x22 cheaper than
   the best hand-written Newton; a `const` array lookup (~700) beats any computation of `2^k` or
   `10^k`; a comparison tree (msb: 4,820) beats arithmetic binary search (14,450).

**Rules of thumb**

- *Type ranking* (add / mul / div): felt252 100/100/- < u8..u64 370/370/910 < u128 270/**3,030**/1,380
  ~ i8..i64 640/640/**4,220** < i128 370/**7,350**/4,690 < u256 2,170/**13,880**/6,050. u8, u16, u32
  and u64 cost exactly the same: never pick a small type for gas. Stay at or below 64 bits for
  multiplications: `u64_wide_mul` is 100 gas whereas `u128 *` is 3,030 and `u128 wide_mul` 3,230.
- *Never write fixed-point mul through the next wider checked `*`*: Q32.32 via `u128 *` = 4,880,
  via u256 = 20,750, via `wide_mul` + `/` = 1,850, via BoundedInt = 1,380.
- *Signed integers are viable for add/sub/mul/compare, not for division.* i64 `+`/`*` cost
  640 / 968 marginal (+30-70% over u64), comparisons cost the same as unsigned, but `/` is 4,220
  (x4.6 u64) unless the divisor is a constant (1,780). i128 `*` is 7,350. A signed Q32.32 on i64
  is best done with `i64_wide_mul` (100) + a BoundedInt biased div_rem: **1,850** vs 2,990 native
  and 2,290-2,760 for a sign-magnitude struct (which additionally makes add/sub branchy).
- *BoundedInt tricks pay off*: -25% to -88% on every kernel tried, and the gain compounds when
  several operations share one final check (dot3 i64: 2,250 vs 6,260 native vs 12,580 naive).
  Costs: `#[feature("bounded-int-utils")]` internal API, helper impls whose ranges must be exact
  (a wrong range is a compiler panic at the Sierra stage, not a type error), and a choice of
  rounding (floor is branchless and cheaper; truncation needs a sign split). No gain for plain
  u64 `/ 2^k` or `% 2^k` (corelib already compiles to the same libfunc).
- *Accumulate wide, rescale once*: 3 x fpmul + 2 adds = 9,290; 3 x wide_mul + one division = 2,790.
- *Defer overflow checks*: summing in felt252 or BoundedInt and narrowing once (570-740) beats
  per-operation checked adds (1,310). Widening conversions are free; a narrowing is 270-540.
- *Avoid `wrapping_*`, `overflowing_*`, `saturating_*` and `checked_mul`* on hot paths: 2-3x the
  plain operator (770 vs 370 for add, 1,110-1,410 vs 370 for mul). `checked_add/sub` are free.
- *Use `DivRem::div_rem` whenever both results are needed*: `x / y` and `x % y` are not merged
  (1,920 vs 910).
- *Shifts*: there is no shift operator. `x / 2^k` = 910, checked `x * 2^k` = 370 (u64) but 3,130
  on u128 (use downcast + bounded mul: 370). Variable shifts need a pow2 table: ~2,600-3,200.
- *Bitwise is fine when it replaces a loop or many divisions, otherwise prefer `%`, `/`, compare.*
  Its first use in a call chain adds the `Bitwise` implicit to every function on the path (~400-500
  gas per non-inlined call).
- *Unroll everything with a static size* (vectors, 3x3 / 4x4 matrices): 753 per element vs 1,840
  in the cheapest loop and 3,280 in a `while i < n` loop. If a loop is unavoidable, iterate the span
  (`for x in span`) rather than indexing, and accumulate in felt252 when ranges allow (-25%).
- *Branches are cheap* (300-400; compare + select ~830): do not replace them with "branchless"
  arithmetic, it is x2 worse (840-1,610) because of the narrowing range check.
- *Lookup tables*: `const [T; N]` + `.span()[k]` (~700-800 per lookup) beats `match` (~2,000) and
  everything computed. Hoist the `.span()` when doing several lookups.
- *Data layout*: struct = tuple = fixed-size array = plain locals when inlined (0 overhead); by
  value = by snapshot (0 difference). Across a non-inlined call each field costs ~100 gas per call;
  box structs of ~8+ fields that cross call boundaries. Prefer `[T; N]` to `Array`/`Span` for
  static sizes (destructure ~150-200 per element vs ~1,020 per bounds-checked index; use
  `multi_pop_front::<N>()` to read N span elements with one check, ~370 per element). Avoid
  `Felt252Dict` in numeric kernels (~6,500 per insert, ~1,900 per get, squash included).
- *Function calls cost ~2,100-2,400 gas* (more than 5 u64 additions). The compiler inlines small
  and medium functions by itself but not large ones; put `#[inline(always)]` on hot numeric
  kernels that are called from few places (-15% on the large case, -70% on a one-liner that was
  forced out of line).
- *felt252 arithmetic is the cheapest thing in Cairo* (100 gas, no range check) but has no order,
  no integer division, and coming back to an integer costs 270-640: use it (or BoundedInt, which is
  the typed version of the same idea) for intermediate accumulations, not as the storage type of a
  number that needs comparisons.
